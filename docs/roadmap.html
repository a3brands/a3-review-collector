Where the system actually is

There are two programs. The Collector (Python) watches listings and stores reviews in SQLite. The Responder (Node) drafts replies, runs the dashboard, and sends the approval emails. The Collector pushes new reviews into the Responder.

Both work. Both are shaped for exactly two dealerships, and neither of them is shaped for a customer who is not A3.

The one that is not a scaling problem

A single shared username and password guards the whole dashboard. Any customer given a login can read every other customer's reviews and performance figures. With two friendly dealerships that is untidy; with paying customers it is a breach. This is why per-customer login sits in the first phase rather than a later one.

The work, in order

Each phase is buildable only once the one above it lands. Estimates are developer-days for one person who knows this codebase, and exclude review and client turnaround.

P0 Clear the deck 2–3 days

Refactoring on top of a suite that is already failing means never knowing which breakage you caused. This is the cheapest phase and it makes every later one measurable.

Deliverables

  • Green test suites in both repos, run automatically rather than by hand.
  • A written triage of every known bug, so "fix the issues" has a definition and an end.
  • An error report that reaches a person — right now a failure is only visible in a log file on the laptop.
P1 Customers live in the database 5–8 days

This is the phase that turns the system from an installation into a product. Until a customer can be added by filling in a form, the ceiling is however many redeploys you are willing to do.

Deliverables

  • A customers table holding name, locations, profile URL, place ID, notification addresses and approver — everything currently hardcoded or in env vars.
  • Per-customer credentials stored encrypted, not as environment variables.
  • An admin screen to add a customer, edit one, and switch one off — no redeploy.
  • A migration that moves the two existing dealerships in with no change to what they see.
P2 Per-customer login and isolation 3–5 days

The breach described above. It has to be closed before a single non-A3 customer is given a login, which makes it the true gate on selling anything.

Deliverables

  • Real accounts with per-customer passwords, replacing shared Basic auth.
  • Every query scoped to the signed-in customer, enforced in one place rather than route by route.
  • An A3 staff role that can see across customers, deliberately and visibly.
  • A test that proves customer A gets a 404 on customer B's review.
P3 State that survives a restart 3–4 days

Pending and approved replies already survive a restart — they are written to disk, not held in memory. What they do not survive is concurrency: each write reads the whole JSON file, edits it and writes it back with no locking, so two approvals landing together lose one. The file is also local to one machine, which caps the app at a single process however large the server is.

Deliverables

  • Pending and approved replies moved from JSON files into the database, where a write is atomic.
  • Reviews served from the database rather than parsed out of JSON files, with paging and indexes.
  • SQLite to Postgres, which is also what makes more than one process possible.
P4 Collection that reaches thousands 5–10 days · blocked

The genuine ceiling, and the one phase that is not purely a matter of effort. Driving a real browser per listing every 15 minutes does not reach thousands of customers at any price.

Deliverables

  • Google Business Profile API as the primary backend — one authorised call per location instead of a rendered page.
  • A work queue with per-customer scheduling, so checks spread across the hour instead of running as one loop.
  • Check frequency tied to how often a listing actually changes, rather than every listing every 15 minutes.
  • Scraping kept only as the fallback for platforms with no API.
Blocked, and not by us

GBP API access is still pending, along with the mailbox and DNS, on one outstanding IT request. This phase cannot start until that clears, and it is on the critical path to launch — which makes chasing it the highest-value thing on this page that is not writing code.

P5 The server 3–5 days

Requirement 4. Deliberately after P1–P3: moving the current two-dealer shape onto a server means doing the move twice, and the second move is the one with customers watching.

Deliverables

  • Both services running as managed services that restart on their own, on a stable public hostname with a real certificate.
  • Nightly database backups, tested by restoring one.
  • Deploy from a repository, not by copying files.
  • Uptime and error alerting that reaches a phone.
P6 Onboarding and running it 4–6 days

The difference between a system that can hold thousands of customers and a business that can actually sign them. Every step here is one a developer currently has to perform by hand.

Deliverables

  • A guided flow that takes a new dealership from Google authorisation to first collected review without a developer.
  • Usage and cost per customer, so pricing is based on figures rather than a guess.
  • An internal runbook: what breaks, how it shows, what to do.
  • The customer user guide linked from the dashboard itself.

Requirement 4 — where it runs

Three realistic options. The system needs a US IP address (DealerRater and Carfax refuse other traffic — today that is worked around with a VPN), a real browser for the scraping fallback, a database, and no dependency on anyone's laptop.

Recommendation

A US VPS. It is the only option that is cheap, removes the VPN dependency, and leaves browser scraping workable while the GBP API is still blocked. Postgres runs on the same box at this size and moves to a managed service later without changing the application. Revisit at roughly 200 customers or the first time one box stops keeping up — whichever comes first.

Sequence and honest timing

P0 through P3 is roughly three to four weeks of focused work and produces a system that is genuinely multi-customer, safe to give logins for, and does not lose work on restart. P5 adds a week and takes the laptop out of the picture.

P4 is the one that decides the ceiling, and it is waiting on an IT request rather than on development time. Until it clears, "thousands of customers" is a design the code is ready for rather than a load it can carry. Everything else can be built while waiting.

The soonest honest answer to "can we sell this" is after P2, to a small number of customers, on a server. Selling before P2 means every customer can read every other customer's reviews.

Requirement 5 — how this gets run

Rhea owns the project: scope, sequence, and what ships. A suggestion for keeping that concrete rather than implicit:

  • One phase at a time, each with the deliverables above as its definition of done. No phase starts before the one before it is finished and demonstrated.
  • A demo at the end of each phase, against real dealership data, not a test fixture. The demo is the sign-off.
  • The blocked items get chased weekly. The GBP API, the mailbox and DNS are one request, and it sits on the critical path to launch.
  • Changes to scope get written down here, so the plan stays the thing everyone is arguing with rather than a memory of a meeting.
